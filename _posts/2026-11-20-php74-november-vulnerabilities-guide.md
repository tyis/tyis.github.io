2026年10月、PHPに認証不要のリモートコード実行につながる重大な脆弱性 **PHP2Shell（CVE-2026-109618 / CVE-2026-109619）** が公表されました。サポート終了（EOL）であるPHP 7.4についても、Debian/Ubuntu向けのSuryパッケージやEL系のRemiパッケージがバックポート版を公開し、**PHP 7.4.33-31** へのアップデートで対応を終えた企業も多いと思います。

しかし、その対応は **「10月分」** です。

2026年11月19日、PHPの新しいセキュリティリリース（8.2.36 / 8.3.37 / 8.4.28 / 8.5.13）が公開され、**17件の脆弱性** が新たに修正されました。そのうち **7件はCVSS v4.0で9.2（Critical）** です。そして、その一部はPHP 7.4のコードにも存在します。

本記事では、「7.4.33-31まで適用したから大丈夫」と考えている環境を前提に、残っているリスクと今後の対応を整理します。

## まず結論

| 質問 | 回答 |
|------|------|
| PHP2Shellは7.4.33-31で解決したか | **はい。** Sury版・Remi版とも-31にバックポートが含まれます |
| 11月の脆弱性も7.4.33-31で解決したか | **いいえ。** 11月分のバックポートは、その次のリビジョンで公開されています |
| `php -v` で確認できるか | **できません。** バージョンは7.4.33のまま変わらないため、パッケージのリビジョンで確認します |
| WAFを入れれば代わりになるか | **なりません。** 一部の攻撃パターンは緩和できますが、構造的に防げないものがあります（後述） |

## 11月に公表された脆弱性のうち、PHP 7.4に関係するもの

11月の修正対象はサポート中の8.2〜8.5系統ですが、脆弱性コード自体が古い系統から存在するものがあります。PHP 7.4環境で特に確認すべきものは以下です。

| CVE | 深刻度 | 概要 | 主な影響条件 |
|-----|--------|------|-------------|
| **CVE-2026-129289** | Critical 9.2 | PHP-FPMリクエストスマグリング。読み残したリクエストボディが次のFastCGIリクエストとして解釈される | フロント側でFastCGI接続を再利用する場合（NGINXの `fastcgi_keep_conn on`、Apacheの `enablereuse=on` など）。問題のコードはPHP 5.6から存在 |
| **CVE-2026-115560** | Critical 9.2 | セッションシリアライザの不整合によるコード実行の可能性 | `session.upload_progress` が有効で、シリアライザの異なるアプリ・プール・CLIジョブがセッション保存先を共有する場合など。PHPは「8.2より古いサポート終了リリースも影響を受ける可能性がある」と案内 |
| **CVE-2026-126714** | Critical 9.2 | 書き込みが中断されたセッションファイルによるコード実行の可能性（phpAfterShell） | 標準の `files` セッションハンドラで、攻撃者がセッションデータを制御でき、書き込みが適切なタイミングで中断される場合 |
| **CVE-2026-129496** | Critical 9.2 | タイムゾーンキャッシュの解放後使用（use-after-free） | 起動時診断がファイルのerror_logに記録される構成で、新規ワーカーの初回リクエスト時に診断が発生する場合 |
| **CVE-2026-129291** | High 8.8 | PHP-FPMのepoll処理における解放後使用、ローカル権限昇格 | `catch_workers_output` が有効で、すでにFPMワーカー内でコード実行できることが前提 |

このほか、PHAR署名検証の回避（CVE-2026-128090）、HTTPS/FTPSの平文化（CVE-2026-128064）、折り返しヘッダによるDoS（CVE-2026-127960）、PHP-CGIの境界外読み書き（CVE-2026-129538）なども、バックポート対象に含まれています。

一方で、CVE-2026-129481はPHP 8.3以降、CVE-2026-129474 / CVE-2026-129182はPHP 8.5のみが対象であり、**7.4には関係しません。** 「17件すべてが7.4に当てはまる」わけではない点も、正確に把握しておくことが重要です。

### 危険度の捉え方

11月のCriticalはいずれも「既定とは異なる設定や、一般的ではない構成」が条件になると事前予告されていました。裏を返せば、**自社環境の構成を確認するまでは「対象外」とは言い切れない** ということです。

- FastCGI接続の再利用を有効にしていないか
- `session.upload_progress` が有効なままになっていないか
- セッション保存先を複数のアプリやバッチで共有していないか
- `catch_workers_output` を有効にしていないか

この4点を確認するだけで、主要なCriticalの大半は対象かどうかを切り分けられます。

## 自社環境の確認方法：バージョンではなくリビジョンを見る

EOL系統へのバックポートでは、**PHPのバージョン番号は変わりません。** アップデート後も `php -v` は `PHP 7.4.33` と表示されます。確認はパッケージ側で行います。

### Debian / Ubuntu（Suryパッケージ）の場合

```bash
# パッケージリビジョンの確認（1:7.4.33-37 以降が11月分を含む現在のビルド）
dpkg -l | grep php7.4

# changelogで11月のCVEが含まれるか確認
zgrep CVE-2026-129289 /usr/share/doc/php7.4-common/changelog.Debian.gz
```

Suryパッケージでは、11月分のバックポート（8.2.36から移植）は **リビジョン-36** で入り、現在のビルドは **-37** です。**-31は10月のPHP2Shell分まで** です。

### EL8 / EL9 / EL10（Remiパッケージ）の場合

```bash
rpm -q php-cli php-fpm
rpm -q --changelog php-common | grep -m1 CVE-2026-129289
```

Remiでは11月分のバックポートが **7.4.33-32** として公開されています（EL8/9/10向け）。

### CentOS 7の場合：公式ビルドが存在しない

注意が必要なのがCentOS 7です。RemiのEL7向けリポジトリはCentOS 7のサポート終了に伴い **7.4.33-15で凍結** されており、PHP2Shellの修正すら公式ビルドでは提供されませんでした。

CentOS 7でPHP 7.4を運用している場合は、次のいずれかが必要です。

1. EL8/9向けのソースRPM（SRPM）をEL7でリビルドする（specファイルにはEL7向けの条件分岐が残っていますが、ICUなどの依存ライブラリのバージョン調整が必要です）
2. EL7向けにバックポート版を提供しているサードパーティのビルドを利用する（提供元の信頼性と、パッケージの出所を必ず確認してください）
3. **根本対策として、OSとPHPの両方をサポート中のバージョンへ移行する**

1と2はあくまで延命策です。CentOS 7もPHP 7.4もサポート終了製品であり、脆弱性が公表されるたびに同じ問題が繰り返されます。

## WAF（ModSecurity）では防げないのか

「パッチが難しいので、WAFで防げないか」という相談もよくあります。結論から言えば、**WAFはパッチの代わりにはなりません。** CVEごとに見ると理由が分かります。

| CVE | WAFでの防御 | 理由 |
|-----|-------------|------|
| PHP2Shell（109618/109619）、115560 | **一部のパターンのみ** | 確認されている攻撃経路は `PHP_SESSION_UPLOAD_PROGRESS` フィールドを含むmultipart POSTのため、このフィールドを遮断するカスタムルールが実攻撃を防いだ事例はあります。ただしOWASP CRSの標準ルールにはこのフィールドを対象とする専用ルールがなく、追加設定が必要です。変形したmultipartによる回避も報告されています |
| 126714（phpAfterShell） | **ほぼ不可** | リクエスト自体は正常なセッションリクエストと見分けがつかず、本質はセッションファイルの書き込みタイミングの問題です |
| 129289（FPMスマグリング） | **構造的に不可** | スマグリングされた第2のリクエストは、最初のリクエストの未読ボディの中にFastCGIレコードとして隠れてFPMへ直接渡ります。**HTTPリクエストとしてWAFを通過しない** ため、WAFが見ているのは正常な最初のリクエストだけです |
| 129496 / 129291 | **不可** | サーバー内部の状態やローカルな前提条件が問題であり、HTTPのシグネチャ自体が存在しません |

商用WAF/IPSでは仮想パッチ（バーチャルパッチ）として専用ルールが提供される場合がありますが、オープンソースのModSecurity + OWASP CRSを導入しただけでは自動的には付いてきません。

すでにWAFを導入済みの環境であれば、upload-progressフィールドを遮断するカスタムルールを追加するのは「追加の防御層」として意味があります。しかし、**この目的のためだけにWAFを新規導入するのは順序が逆** です。次に挙げる設定変更の方が、確実で、安く、早く終わります。

## パッチ適用までの暫定対策（設定変更で今日できること）

いずれも設定変更とPHPプロセスの再起動だけで完了します。

```ini
; 1. セッションアップロードプログレスを無効化（109619 / 115560 / 126714の主要経路を遮断）
session.upload_progress.enabled = 0
```

```nginx
# 2. NGINX: FastCGI接続の再利用を無効化（129289対策、既定値も off）
fastcgi_keep_conn off;
```

Apacheの場合は `mod_proxy_fcgi` の `enablereuse=on` を外してください。

```ini
; 3. FPMプール: ワーカー出力の捕捉を無効化（129291対策）
catch_workers_output = no
```

4. `date.timezone` の未設定など、起動時に診断メッセージが出る原因を取り除く（129496対策）
5. `post_max_size` やWebサーバー側のリクエストボディ上限を実利用に合わせて引き下げる（OOMを狙う攻撃のコストを上げる）

注意点として、暫定対策は **「主要な経路を塞ぐ」** ものであり、脆弱性そのものを直すものではありません。バックポート版の適用は別途必要です。

## 今後の対応：推奨する進め方

### 短期（今週中）

1. 管理下の全サーバーでPHPのパッケージリビジョンを棚卸しする（`php -v` ではなくパッケージで）
2. 上記の構成確認4点（FastCGI再利用、upload_progress、セッション共有、catch_workers_output）を実施する
3. 暫定対策（設定変更）を適用し、PHP-FPM / Webサーバーを再起動する
4. 配布元ごとの11月分バックポート（Sury: -37以降 / Remi EL8-10: -32）を適用する

### 中期（計画として）

PHP 7.4は2022年11月にサポートが終了しており、今回のような「公表のたびにバックポートの有無を確認する」運用は今後も続きます。バックポートは配布元の善意に依存し、提供が止まればその時点で無防備になります。

- PHPはサポート中の **8.3 / 8.4** への移行を計画する（8.2も2026年末でセキュリティサポート終了予定です）
- CentOS 7などOS自体がサポート終了の場合は、OS移行とセットで計画する
- 移行までの期間は、「脆弱性公表 → 自社リビジョン確認 → バックポート適用」を定型手順として運用に組み込む

## まとめ

- PHP2Shellへの対応（7.4.33-31）は正しく完了しています。ただし、それは **10月分まで** です
- 11月の脆弱性のうち、FPMスマグリングやセッション関連など **7.4にも届くもの** が複数あります
- 確認はバージョン番号ではなく **パッケージリビジョン** で行います
- WAFは一部の攻撃パターンを緩和できますが、**FPMスマグリングのように構造的に防げないもの** があり、パッチの代替にはなりません
- 暫定対策（設定変更）で主要経路を塞ぎつつ、バックポートを適用し、中期的にはサポート中のPHPへの移行を進めることが、現実的な対応です
